## 三、移植策略：每个模块由 AI 自行评估

> 本节说明**每个 WBS 任务应该怎么干**。执行者（人或 AI）接到 `T-x.y` 任务后，**先按本节做出分类判定，再动手**。

### 3.1 核心原则

> **不要把「Kotlin 文件」当成移植单位，要把「测试文件」当成移植单位。**
>
> 测试是行为契约——必须保证；实现是达成方式——可以自由重写。
>
> 移植契约 + 重写实现 = 又对又像 Flutter 的代码。

### 3.2 可参考的原始资产

原项目就在同一个仓库里，**动手前先查这些**：

| 资产 | 路径 | 价值 |
|---|---|---|
| 原实现 | `app/src/main/java/moe/ouom/neriplayer/`（637 文件 / 198,769 行） | 语义参照 |
| **纯逻辑测试** | `app/src/test/`（**353 个零 Android 依赖的测试文件**） | ⭐ **可执行的规格说明书** |
| 设备测试 | `app/src/androidTest/`（70 文件 / 15,131 行） | 集成行为参照 |
| 一起听服务端 | `np-submodule/NeriPlayer-LTW/`（含 5 个协议测试） | 协议契约，零改动复用 |
| 原项目 README | `README.md` | 完整功能与使用说明 |
| 归档历史文档 | `docs/archive/` | 仅供追溯，**不作为依据** |
| 功能对照表 | `docs/Flutter移植功能对照表.md` | 248 项功能点的保留 / 降级 / 移除决定 |

> **关键数据**：421 个 JVM 单测里，**353 个（84%）零 Android 依赖**；`ui/` 目录下也有 70 个。
> 说明原项目已经把「行为契约」和「实现方式」分离好了——UI 里能脱离 Android 的逻辑全都抽成了纯函数并写了测试。

### 3.3 分类判据

拿到一个任务，先问：**这个模块的产出是什么？**

| 类型 | 判断依据 | 典型例子 | 占比 |
|---|---|---|---|
| **A 事实型** | 改了就会对接不上；内容是逆向工程成果 | `NeteaseCrypto` 的 `PRESET_KEY` / `IV` / 公钥；QQ 音乐 QIMEI 规则；酷狗签名；LRC/YRC/TTML 时间戳规则；34 张表结构；152 个设置项 key | ~25% |
| **B 逻辑型** | `app/src/test/` 下有对应测试 | 32 个播放 policy；一起听漂移校正；下载续传策略；统计合并与榜单门槛；歌词解析 | ~35% |
| **C 表现型** | 产出是用户看到的画面 / 动画 / 交互 | Now Playing 布局；歌词逐字高亮动画；玻璃模糊；流体背景；设置页交互 | ~30% |
| **D 基础设施** | Flutter 有成熟替代品 | Room→Drift；OkHttp→Dio；DataStore→shared_preferences；ExoPlayer→just_audio / media_kit；KSP→build_runner | ~10% |

> 一个任务可以混合多种类型，标注比例即可（例如 `T4.3 Now Playing = C 70% + B 30%`）。

### 3.4 每类的打法

#### A 事实型 → 照抄，禁止发挥

- 常量、URL、字段名、密钥**逐字对照**
- 不重命名、不「优化」、不合并、不调整顺序
- 好处：写错了立刻会炸，不会静默出错

#### B 逻辑型 → 测试优先（主力打法）

```
1. 读原测试文件 → 产出「行为清单」（输入 → 期望输出 的表格）
2. ⚠️ 人工 review 行为清单        ← 唯一必须人工介入的点
3. 生成 Dart 测试骨架（先全部标红）
4. 读 Kotlin 实现 → 只提取「意图」，不提取「写法」
5. 写 Dart 实现 → 跑到测试全绿
6. ⚠️ 人工抽查代码风格         ← 防止写出 Kotlin 味的 Dart
```

#### C 表现型 → 看效果原创，不读实现

- **不要读 Compose 源码来翻译**，否则必然写出 Kotlin 味的 Dart
- 参考素材：跑一遍原版 App / 看截图 / 读需求描述
- Kotlin 源码**只用它回答「这个页面上有什么」，不用它回答「怎么布局」**
- 验收靠人眼，没有客观标准——**这正是 UI 慢、且占 30% 人天的根本原因**

#### D 基础设施 → 换生态，不模仿原 API

- 直接采用 Flutter 生态方案
- 只把「数据结构」和「配置项」搬过来

### 3.5 ⚠️ 两条已被验证的失败路径

#### 失败路径 1：纯原创（照功能清单从零写）

会漏掉藏在测试里的隐性需求。以下是本项目真实存在的例子：

| 模块 | 隐性需求 | 出处 |
|---|---|---|
| 长音频进度记忆 | 仅对时长 **≥15 分钟** 的内容保存；**<5 秒** 的位置不写入；距结尾 **30 秒** 内视为已完成并清零 | 有对应单测 |
| 热点榜单 | 周榜门槛累计收听 **≥10 分钟**；月榜 **30 分钟** | 有对应单测 |
| 一起听重连 | `memberSecret` 重连不触发暂停；普通 WebSocket 断线保留成员；成员控制后心跳抑制窗口 **4000ms** | 服务端 README + 测试 |
| 网易云 WebView 登录 | 屏宽 **≥600dp** 用桌面版页面，否则用移动版；UA 按屏宽切换且不能含 WebView 标记 | `NeteaseWebLoginUrlTest` |
| 房间生命周期 | 房主心跳 **45 秒** 超时进入挂起；**10 分钟** 宽限期内可恢复，超时自动关房 | 服务端 README |

> **这些数字原创时一个都想不出来，但全在测试里躺着。**

#### 失败路径 2：纯翻译（逐行读 Kotlin 重写）

两个后果：

1. **写出 Kotlin 味的 Dart**——硬搬 `Flow` / `StateFlow` / `remember` / `derivedStateOf` / `sealed class` 模式匹配
2. **把 Android 特有的绕路一起搬过来，在 Windows 上变成死代码**：
   - 主进程 / 多进程判断（`AppProcessClassifier`）
   - WebView 数据目录后缀处理
   - 前台服务 `onStartCommand` 生命周期
   - SAF `DocumentFile` 树遍历

| 类型 | 验收方式 |

| C | 人工比对原版 App 的视觉与交互 |
